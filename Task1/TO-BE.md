

Выбранный подход: Вынос сервиса ставок из монолита как первый шаг Strangler Fig.

Ниже обоснование:
## Варианты влияющие на выбор архитектуры 

**A. Точечная оптимизация без смены архитектурного стиля**
**Что делаем:** тюнинг тяжёлых запросов и индексов; увеличение ресурсов инстанса PostgreSQL (вертикальное масштабирование); read-replica, на которую переводятся аналитические запросы; буферизация записи событий показов и кликов (пакетная вставка вместо построчной); кеш данных кампаний и кандидатов перед путём ставок; настройка пулов соединений раздельно по типам нагрузки.
**Чего не делаем:** не меняем структуру кода, не выделяем сервисы, не вводим брокер сообщений, не меняем процесс развёртывания.
**Единиц развёртывания:** одна (как сейчас).
**База:** основной инстанс PostgreSQL + read-replica для аналитики. Схема не расщепляется.
**Путь ставок:** там же, где сейчас — внутри монолита, но с кешем перед обращениями к БД.
**Объём:** 4–8 недель, силами текущей команды.

  

**B. Модульный монолит**
**Что делаем**: Модули нарезаем по явным границам (bounded context), деплой остаётся один. Для каждого модуля отдельная схема в БД, каждый модуль владеет своими данными. Межмодульное взаимодействие и доступ к данным других модулей через Facade (публичный интерфейс). Отдельная роль БД на модуль с правами только на свою схему.  
Дополнительно добавляем все то что для варианта А. тюнинг тяжёлых запросов и индексов; увеличение ресурсов инстанса PostgreSQL (вертикальное масштабирование); read-replica, на которую переводятся аналитические запросы; буферизация записи событий показов и кликов (пакетная вставка вместо построчной), реализация через отдельную таблицу-накопитель; кеш данных кампаний и кандидатов перед путём ставок; настройка пулов соединений раздельно по типам нагрузки.
Для распреления трафика установка балансировщика на входе. Для быстрого развертывания и отката добавляем автоматизацию (например ansible)
**Что не делаем**: не выыделяем сервисы, не вводим брокер сообщений, технологический стек не меняем.
**Развертывание**: Развертывание отдельных групп инстансов полноценного приложения под разный трафик для изоляции вычислительных ресурсов (БД остается одна общая)
**База**: основной инстанс PostgreSQL + read-replica для аналитики. Отдельная схема под каждый модуль  
**Для ставок**: отдельные модули для ставок внутри монолита. Отдельные группы инстанса монолита для обработки трафика ставок с кешем перед обращениями к БД
**Объём:** 8-12 недель, силами текущей команды.
  

**C. Вынос сервиса ставок:**
**Что делаем**: Из монолита выносим в отдельный сервис Ad Server и Auction Engine, т. е. те функции, которые отвечают за обработку запросов на аукцион. Этот сервис, назовем bidding service, должен отдавать результат аукциона партнеру менее чем за 80мс.
Установка входного прокси для постепенного (долями) отведения трафика от монолита на выделенный сервис. Реализация будет в API Gateway (из задания 2) где будет в том числе аутентификация, фильтрация и ограничение запросов.
Данные для подбора кандидатов и аукциона загружаются целиком в память процесса саервиса на старте. Далее инкрементальные обнволения чрезе логическу репликацию PG (CDC) напрямую в инстансы сервиса bidding service.  
Остальной монолит меняется по варианту A: read-replica для аналитики, буферизация записи событий через промежуточную таблицу, тюнинг запросов и индексов, раздельные пулы соединений. Для bidding service вводится контейнеризация и автоматизированное развёртывание; монолит пока разворачивается прежним способом.
Что не делаем: не выносим остальной функционал в отдельные сервисы, не вводим брокер сообщений. Delivery Service остаётся в монолите: он обслуживает другой трафик (конечного пользователя, пришедшего за креативом после выигранного аукциона). Нет необходимости менять схему БД (если соответствует требованиям репликации). Не меняем технологический стек
Развертывани: один инстанс монолита под оставшиеся функции. Bidding service масштабируется горизонтально в зависимости от нагрузки. Нагрузку распределеяет прокси. Следует заранее запустить несколько сервисов с запасом так как требуется прогрев сервиса в плане загрузки данных из базы в память.
**База**: основной инстанс PostgreSQL для кампаний и данных для таргетинга + read-replica для аналитики.
**Для ставок**: Полностью отдельный сервис bidding service который отвечает за прием запроса, подбор кандидатов, проведение аукциона и ответ партнеру. Данные полностью из локального снапшота данных, исключаем обращения к БД hot path. Сетевые вызовы в пути ставок — только вход через прокси.
**Объём:** 10-12 недель.

**D. Переписать все на микросервисы:**
**Что делаем:** Выносим каждый монолита компонент в отдельный сервис. Всего 7 сервисов.
Bidding — ранее описан в варианте C
Delivery — подготовка и выдача артефакта рекламы конечному пользователю
Campaign — кампании, параметры таргетинга, настройки
Events — прием и обработка показов и кликов 
Billing — Списание, счета, балансы
Analytics — отчетность рекламодателю (через Dashboard)
Dashboard/BFF — веб-интерфейс кабинета и агрегация данных для него
Между сервисами на пути горячего запроса синхронное взаимодействие через gRPC. Для потока событий показов и кликов асинхронное взаимодействие Kafka. Построение Service Mesh для траффика между сервисами. Установка входного прокси для отведения трафика от монолита на выделенный сервис. Реализация будет в API Gateway (из задания 2) где будет в том числе аутентификация, фильтрация и ограничение запросов.
Своя отдельная база для каждого сервиса. Межсервисных join теперь нет. Аналитика и статистика переводится на отдельное хранилище колоночного типа оптимизированные под агрегаты — ClickHouse.
Данные для подбора кандидатов и аукциона — в памяти процесса Bidding Service, как в варианте C (снапшот при старте, далее инкрементальные обновления из Campaign Service через поток событий Kafka).
Redis используется не как кеш горячих данных, а как хранилище разделяемого состояния: остатки квот бюджета, счётчики частоты показов, лимиты запросов партнёров — то есть то, что изменяется конкурентно и должно быть общим для всех экземпляров Bidding Service
Для списания счета и пополнения баланса реализуется Saga
Инфраструктура создаётся с нуля: контейнеризация всех сервисов, оркестратор (kubernetes), автоматизированные сборка и развёртывание (ci/cd), сквозная наблюдаемость (метрики, логи, распределённая трассировка), приведение сервисов к принципам 12-факторного приложения (конфигурация из окружения, безсостоятельные процессы, логи в поток).
**Чего не делаем:** Монолит не оставляем — выводим из эксплуатации. Промежуточного варианта нет.
**Развертывание**: Cервисы развертываются независимо под оркестратором, каждый масштабируется отдельно. Развёртывание и откат автоматизированы, требуется отдельный контур для миграций схем.
**База данных**: PostgreSQL под транзакционные сервисы (Campaign, Billing). Хранилище под аналитику, кэш под счетчики, брокер для транспорта событий.
**Для горячего пути ставок**: Bidding Service с данными в памяти, обновляемыми из Campaign через поток событий. Обращений к чужим базам нет. Вход через API Gateway.
**Длительность**: 9–12 месяцев. Отсутствие документации потребует изучение кода, воссоздавать логику на схему. Перенос ACID на Saga с компенсациями, создание инфраструктуры (среда запуска, боркеры, кэши и пр). Развертывание и запуск сервисов в соответствии с 12 факторами. Нагрузочное и межсервисное тестирование.
