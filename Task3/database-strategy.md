### Database per Service

| Сервис                           | Тип базы данных                                                                                                                                                             | Обоснование                                                                                                                                                                                                                                                                                                          |
| -------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Сервис ставок** (Bidding)      | Персистентного хранилища нет. Рабочие данные — снапшот в памяти процесса; разделяемое состояние (счетчики) — Redis; журнал аукционов — поток Kafka с загрузкой в ClickHouse | В горячем пути бюджет 60 мс не допускает обращений к БД. Сервис не является мастер-системой ни по одному объекту, требующему сохранности: <br>- кампании принадлежат Campaign и восстанавливаются прогревом,<br>- квоты выдаются Billing. <br>Отсутствие своей БД — не упущение, а следствие модели владения данными |
| **Сервис кампаний** (Campaign)   | PostgreSQL                                                                                                                                                                  | Мастер-данные со связями (рекламодатель → кампания → креатив), требуют транзакций и ссылочной целостности при редактировании. Объём мал (вероятно десятки тысяч активных кампаний), нагрузка на запись низкая, чтения обслуживаются не из БД, а через поток изменений в потребителей                                 |
| **Сервис статистики** (Events)   | Redis — окно дедупликации и журнал последних суток, секционирование по времени; <br>ClickHouse — долговременное хранение фактов                                             | Двухуровневость вынужденная: дедупликация по идентификатору события  в redis - это горячее окно, имеет короткий срок хранения <br> полный поток фактов — в ClickHouse                                                                                                                                                |
| **Сервис аналитики** (Analytics) | ClickHouse                                                                                                                                                                  | Запросы — агрегаты по большим диапазонам (показы, клики, расход по кампаниям за период). Колоночное хранение даёт сжатие в разы и чтение только нужных столбцов; материализованные представления считают агрегаты при вставке. Собственных транзакционных данных сервис не имеет — только производные                |
| **Сервис финансов** (Billing)    | PostgreSQL                                                                                                                                                                  | Проводки и балансы требуют ACID, строгой консистентности и полного журнала операций. Объём умеренный (проводка на оплачиваемое событие), сложность в требованиях к целостности, а не в нагрузке. Идемпотентность списаний реализуется уникальным индексом по идентификатору события — механизм самой СУБД            |

**Прочие компоненты** (вне перечня задания): Delivery — собственных мастер-данных нет, читает креативы из снапшота Campaign, пишет факты показов через таблицу исходящих сообщений в своей PostgreSQL; Dashboard BFF — хранилища не имеет, агрегирует данные сервисов.
