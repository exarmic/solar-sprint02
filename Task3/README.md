
### Данные, масштабирование и отказоустойчивость

Стратегия работы с данными для целевой архитектуры AdScale (горизонт — год), опирающаяся на решения Task1/adr/ADR-001.md и границы сервисов из `Task2`.

| Файл                           | Содержание                                             |
| ------------------------------ | ------------------------------------------------------ |
| `database-strategy.md`         | Тип хранилища для каждого сервиса и обоснование        |
| `scaling.md`                   | Репликация, шардирование, CQRS                         |
| `caching.md`                   | Что кешируется, где, сроки жизни, инвалидация, прогрев |
| `event-streaming.md`           | Топики, схемы событий, группы потребителей, хранение   |
| `failover.md`                  | RPO/RTO, резервное копирование, 12 факторов            |
| diagrams/data-flow.puml        | Потоки данных между сервисами и хранилищами            |
| diagrams/storage-topology.puml | Топология хранилищ: реплики, шарды, зоны доступности   |

**Три принципа**

1. **Тип хранилища определяется характером нагрузки.** Транзакционные данные — реляционная СУБД, аналитические агрегаты — колоночная, конкурентно изменяемые счётчики — хранилище структур в памяти, поток фактов — журнал событий.
2. **Деньги не хранятся в том, что может их потерять.** Единственный источник истины по расходу — проводки в Billing; Redis хранит выданные квоты, Kafka — факты, но ни то ни другое не является учётной системой.
3. **Персональные данные ограничены по сроку хранения.** Идентификаторы пользователей, IP и характеристики устройств попадают в события; в аналитическое хранилище они передаются обезличенными, в журналах хранятся ограниченное время (152-ФЗ).
