### 1. RPO и RTO по сервисам

RPO — допустимый объём потерянных данных, измеряется временем; RTO — допустимое время восстановления. Значения — допущения, подлежат согласованию с бизнесом.

|Сервис / хранилище|RPO|RTO|Чем обеспечивается|Что происходит при отказе|
|---|---|---|---|---|
|Billing (PostgreSQL)|**0**|5 мин|синхронная реплика в другой зоне, автоматическое переключение, непрерывное архивирование журнала|Списания приостанавливаются, события накапливаются в Kafka и обрабатываются после восстановления. Аукционы продолжаются на выданных квотах|
|Campaign (PostgreSQL)|0|15 мин|синхронная реплика, автопереключение|Редактирование кампаний недоступно; Bidding и Delivery работают на снапшоте|
|Events (PostgreSQL, горячее окно)|5 мин|30 мин|асинхронная реплика + переигрывание из Kafka|Обработка событий останавливается, данные не теряются: журнал брокера хранит 7 суток|
|ClickHouse|1 час|4 часа|реплицированные таблицы, повторная загрузка из Kafka|Отчётность недоступна, показы и списания не затронуты|
|Redis (квоты, счётчики)|**допускается потеря**|1 мин|реплика с автопереключением|Квоты запрашиваются заново; максимальный ущерб — одна выданная квота. Счётчики частоты обнуляются — возможен перебор показов|
|Kafka|0|10 мин|фактор репликации 3, минимум 2 синхронные реплики, распределение по зонам|Производители буферизуют в таблицах исходящих сообщений; потребители дочитывают после восстановления|
|Bidding (состояние в памяти)|неприменимо|2 мин|резерв прогретых экземпляров|Трафик перераспределяется на оставшиеся экземпляры|

Ключевое различие в первой и предпоследней строках: RPO = 0 для проводок, потому что потерянное списание — это недополученные деньги, которые нечем восстановить; допустимая потеря состояния Redis — потому что квота восстановима, а её максимальная цена известна заранее и ограничена размером окна.

### 2. Резервное копирование

|Хранилище|Полная копия|Непрерывное архивирование|Хранение|Проверка|
|---|---|---|---|---|
|Billing|ежесуточно|журнал предзаписи, восстановление на точку во времени|35 суток + ежемесячные копии 1 год|ежемесячное пробное восстановление с замером фактического RTO|
|Campaign|ежесуточно|журнал предзаписи|35 суток|ежеквартально|
|Events (PostgreSQL)|ежесуточно|нет|7 суток|ежеквартально|
|ClickHouse|еженедельно|нет: восстановление повторной загрузкой из Kafka и из PostgreSQL|4 недели|полугодовая проверка|
|Redis|не создаётся|—|—|—|
|Kafka|не создаётся: сам является резервной копией потоков на срок хранения|—|—|—|

Копия, восстановление которой ни разу не проверялось, резервной копией не является — отсюда отдельная колонка с регулярностью проверок и замером фактического времени восстановления. Копии хранятся вне зоны доступности основного хранилища.

### 4. Соответствие принципам 12-факторного приложения

| Фактор                    | Как выполнен                                                                                                                                     |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| Кодовая база              | один репозиторий на сервис, развёртывания — из одного источника                                                                                  |
| Зависимости               | объявлены явно, образы контейнеров с зафиксированными версиями                                                                                   |
| Конфигурация              | в переменных окружения: адреса брокера, хранилищ, размеры квот, пороги. В образе конфигурации нет                                                |
| Сторонние службы          | PostgreSQL, Redis, Kafka, ClickHouse подключаются по адресам из конфигурации и заменяются без изменения кода                                     |
| Сборка, релиз, выполнение | раздельные стадии, релиз неизменяем и помечен версией                                                                                            |
| Процессы                  | стейтлес: снапшот в памяти — производная от потока, разделяемое состояние — во внешнем хранилище                                                 |
| Привязка портов           | сервис сам слушает порт, внешний сервер приложений не требуется                                                                                  |
| Параллелизм               | масштабирование числом экземпляров, не размером экземпляра                                                                                       |
| Утилизируемость           | быстрый старт (ограничен прогревом снапшота), корректное завершение: дообработка текущих запросов, подтверждение смещений, снятие с балансировки |
| Паритет сред              | те же образы и те же версии хранилищ в тестовой и рабочей средах                                                                                 |
| Журналирование            | поток в стандартный вывод, сбор внешней системой; файлов журналов сервис не ведёт                                                                |
| Административные задачи   | миграции схем и разовые операции — отдельными задачами на том же образе                                                                          |
