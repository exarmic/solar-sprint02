### Проектирование RTB и интеграции с DSP

Документ описывает архитектуру Bidding Service — компонента, который выносится из монолита AdScale первым срезом (решение зафиксировано в Task1/adr/ADR-001.md), и интеграционный слой для новой DSP-площадки.

**Состав директории**

| Файл                   | Содержание                                                                               |
| ---------------------- | ---------------------------------------------------------------------------------------- |
| `bidding-service.md`   | Границы сервиса, API, зависимости                                                        |
| `interaction.md`       | Выбор протоколов для каждого взаимодействия с обоснованием                               |
| `api-gateway.md`       | Входной слой: аутентификация, ограничение частоты, маршрутизация, размыкатель, замер SLA |
| diagrams/sequence.md   | Диаграмма последовательности: путь ставки и учёт показа                                  |
| diagrams/components.md | C4 Component: внутреннее устройство Bidding Service                                      |

**Требования, из которых выведены решения** (полный набор — Task1/drivers.md):

- 18 000 RPS в пике при P95 ≤ 100 ms; через год — 50 000 RPS;
- доля ответов вне дедлайна партнёра 80 ms — не более 1%;
- отказ зависимости не приводит к отказу пути ставок;
- события показов и кликов не теряются и не задваиваются (из них считаются деньги);
- непрерывность бизнеса: переход долями трафика с возможностью отката за минуты.

**Три решения, определяющие всё остальное**

1. На hot path нет обращений к базам данных и нет синхронных вызовов в монолит.  Активные кампании и параметры таргетинга лежат в памяти процесса.
2. Бюджет кампании выдаётся квотами, а не реплицируется: атомарное уменьшение общего счётчика ограничивает перерасход известной величиной 
3. Повторные попытки в горячем пути запрещены. Опоздавший ответ в аукционе бесполезен, поэтому вместо повтора — быстрый отказ от участия (no-bid).
